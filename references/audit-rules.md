# The 24 rules

Every rule exists because the defect is cheap to introduce, expensive to discover,
and invisible in a passing test suite. Each one lists what it catches, why it
matters, and what fixes it.

A rule is a judgement, not a law. Context overrides all of them — the point is
that the decision should be deliberate.

---

## Critical

### `no_primary_key`

**Catches** a table with no primary key.

Rows cannot be addressed unambiguously. You cannot update or delete one row
without hoping the rest of its column values are unique. Logical replication
refuses the table outright, most ORMs cannot map it, and `UPDATE ... LIMIT 1`
becomes the only tool available.

```sql
ALTER TABLE t ADD COLUMN id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY;
```

### `fk_without_constraint`

**Catches** `user_id`, `post_id`, `uploaded_by`, `parent_id` — a column whose name
names another table, with nothing enforcing that the row exists.

This is the defining defect of generated schemas. The column is there, the
intent is obvious, and the database will still happily store `99999` pointing at
nothing. Orphans accumulate silently: no error, no log line, just rows that join
to nothing and reports that quietly undercount. The only thing protecting
integrity is application code that every future caller has to remember.

Inference covers `<table>_id`, `<table>Id`, `<table>_uuid`, `*_by` (conventionally
`users`), and self-references such as `parent_id`.

```sql
ALTER TABLE posts ADD CONSTRAINT fk_posts_user_id
  FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE RESTRICT;
CREATE INDEX idx_posts_user_id ON posts (user_id);
```

### `plaintext_secret`

**Catches** `password`, `token`, `api_key`, `secret` as a plain column, with no
`_hash` or `_encrypted` in the name.

If this holds the real value, one `SELECT`, one leaked backup, or one verbose log
line exposes every account at once. Passwords must be one-way hashed with argon2id,
bcrypt or scrypt. Tokens must be hashed or encrypted at rest.

```sql
ALTER TABLE users RENAME COLUMN password TO password_hash;
```

## High

### `unindexed_fk`

**Catches** a declared foreign key with no index on its columns.

The most common performance defect in generated schemas, and the most
deceptive — the constraint is right there, so the schema looks careful. Two
things then degrade with row count: every join through the key becomes a
sequential scan, and every delete on the parent must scan the child table to
check the constraint. Fast at a thousand rows, unusable at a million, with no
single moment where it broke.

Most databases index a primary key automatically. Almost none index a foreign key.

```sql
CREATE INDEX idx_posts_user_id ON posts (user_id);
-- large PostgreSQL table: CREATE INDEX CONCURRENTLY
```

### `no_cascade_rule`

**Catches** a foreign key with no `ON DELETE`.

The default is `NO ACTION`: deleting a parent raises a constraint error. That is
rarely what anyone wanted, and it is discovered in production when the first
delete fails. The right behaviour is a design decision — `CASCADE` for genuinely
owned children, `RESTRICT` to refuse deliberately, `SET NULL` for optional links.
Inheriting the default is not choosing.

```sql
ALTER TABLE comments
  ADD CONSTRAINT fk_comments_post FOREIGN KEY (post_id)
  REFERENCES posts (id) ON DELETE CASCADE;
```

### `boolean_as_text`

**Catches** `is_active`, `has_paid`, `approved` typed `TEXT`/`VARCHAR`.

`'true'`, `'True'`, `'TRUE'`, `'1'`, `'yes'` and `'t'` are six distinct values
that all mean the same thing, and nothing stops any of them being written. Every
read needs string comparison, and `WHERE is_active = 'true'` silently misses rows.

```sql
ALTER TABLE users ALTER COLUMN is_active TYPE boolean
  USING (lower(is_active) IN ('true','t','1','yes'));
```

### `timestamp_as_text`

**Catches** `created_at`, `published_at`, `*_date` typed `TEXT`.

Text timestamps sort lexicographically, so `'2026-1-5'` sorts before `'2026-01-10'`
and any `ORDER BY created_at` is subtly wrong. Range queries cannot use an index
usefully. Two writers using different formats is undetectable until something
tries to parse the column.

```sql
ALTER TABLE posts ALTER COLUMN created_at TYPE timestamptz
  USING created_at::timestamptz;
```

### `numeric_as_text`

**Catches** `view_count`, `total`, `quantity` typed `TEXT`.

`'10' < '9'` is true for strings. Sorting a leaderboard by a text count produces
nonsense, `SUM` requires a cast that defeats indexes, and nothing prevents
`'none'` being written into the column.

```sql
ALTER TABLE posts ALTER COLUMN view_count TYPE bigint USING view_count::bigint;
```

### `money_as_float`

**Catches** `price`, `amount`, `total`, `balance` typed `FLOAT`, `REAL` or `DOUBLE`.

Binary floating point cannot represent `0.10` exactly. Sum enough rows and the
total drifts by fractions of a cent, invoices stop reconciling, and the
discrepancy is unreproducible because it depends on addition order. This is a
correctness bug in anything that handles money.

```sql
ALTER TABLE orders ALTER COLUMN total TYPE numeric(12,2);
-- or store minor units as bigint cents and format on output
```

### `missing_unique`

**Catches** `email`, `slug`, `username`, `sku`, `uuid` with no unique constraint.

Duplicates are not a possibility, they are a certainty under concurrency: two
requests check whether the email exists, both see nothing, both insert. An
application-level check cannot close that window. Only the database can.

```sql
ALTER TABLE users ADD CONSTRAINT uq_users_email UNIQUE (email);
```

### `nullable_everything`

**Catches** a table where 80% or more of non-key columns are nullable.

The signature of a schema transcribed from a wishlist rather than designed. When
everything is optional the schema enforces nothing, every reader must handle NULL
for fields that are in practice always present, and the genuinely optional columns
become indistinguishable from the accidents.

```sql
-- backfill first, then constrain only what is truly required
ALTER TABLE posts ALTER COLUMN title SET NOT NULL;
```

## Medium

### `enum_as_free_text`

**Catches** `status`, `role`, `type`, `state` as `TEXT` with no `CHECK`.

The set of legal values exists only in someone's head. One code path writes
`'published'`, another writes `'PUBLISHED'`, a third writes `'live'`, and no
reader handles all three. The database accepted every one of them.

```sql
ALTER TABLE posts ADD CONSTRAINT chk_posts_status
  CHECK (status IN ('draft', 'published', 'archived'));
```

### `json_as_text`

**Catches** `metadata`, `payload`, `config`, `settings` as `TEXT`.

As text it cannot be queried, indexed or validated. Malformed JSON is stored
without complaint and only discovered when something tries to read it.

```sql
ALTER TABLE media ALTER COLUMN metadata TYPE jsonb USING metadata::jsonb;
```

### `timestamp_without_timezone`

**Catches** PostgreSQL `timestamp` rather than `timestamptz` on a time column.

The value records a wall-clock reading with no offset, so the same column means
different instants depending on which server wrote it. The most prolific source
of off-by-hours bugs, and it survives every test run on a machine set to UTC.

```sql
ALTER TABLE events ALTER COLUMN occurred_at TYPE timestamptz;
```

### `duplicate_rows_possible`

**Catches** a join table with a surrogate `id` and no unique constraint on the
foreign key pair.

Nothing stops the same relationship being inserted twice. A retried request
silently creates a duplicate, and then every query joining through the table
multiplies rows — a bug that looks like bad data, not a bad schema.

```sql
ALTER TABLE post_tags ADD CONSTRAINT uq_post_tags_pair UNIQUE (post_id, tag_id);
-- a composite primary key is usually better than a surrogate id here
```

### `fk_type_mismatch`

**Catches** a foreign key narrower or wider than the key it references.

Mismatched widths force an implicit cast on every join, which can stop the index
being used at all, and the narrower column overflows before the table it
references does.

```sql
ALTER TABLE b ALTER COLUMN a_id TYPE bigint;
```

### `missing_timestamps`

**Catches** a table with no `created_at`.

You cannot order history, reconstruct an incident, expire old rows or build any
time-series view. Unlike most defects this one is unrecoverable: the information
was never written down.

```sql
ALTER TABLE t ADD COLUMN created_at timestamptz NOT NULL DEFAULT now();
```

### `unbounded_text`

**Catches** `email`, `slug`, `url`, `phone` with no length bound.

Nothing stops a megabyte being written into a field meant for an email address.
On MySQL an unbounded column also cannot be fully indexed. On PostgreSQL this is
mostly stylistic — `text` is idiomatic there — so it is reported as low severity.

```sql
ALTER TABLE users ALTER COLUMN email TYPE varchar(255);
```

## Low

### `no_updated_at`

A table with `created_at` and no `updated_at`. Caching, incremental sync and audit
trails all need to know when a row last changed. Skipped for pure join tables,
which have nothing to update.

### `inconsistent_naming`

`snake_case` and `camelCase` in one table. Every query becomes a guess about
quoting, and on PostgreSQL a camelCase identifier requires double quotes forever.

### `reserved_word_column`

A column named `order`, `key`, `user`, `value`, `group`. Every reference must be
quoted, in every query and every ORM, and one unquoted use is a runtime syntax
error.

### `redundant_index`

An index whose columns are a prefix of a wider index. The wider one already serves
every query the narrower one does; the extra index costs write throughput and
storage for no read benefit.

### `wide_table`

More than 30 columns. Usually several entities wearing one name. Forces
`SELECT *` to read cold data and makes row locks coarser than they need to be.

## Adding a rule

One function in `scripts/audit.py`, appending to `out`:

```python
out.append(finding(
    "high", "rule_name", table_name,
    "What is wrong, in one sentence.",
    "Why it will hurt, concretely.",
    "ALTER TABLE ... ;",     # the fix -- never omit this
    [column_name],
))
```

Then a test in `tests/test_schemascope.py` asserting the rule fires on a schema
that has the defect, and a second asserting it does *not* fire on one that does
not. The second test is the one that matters: a rule with false positives makes
the whole report ignorable.
